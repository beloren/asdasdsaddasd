# PvP Extraction Simulator

Проект почти полностью серверный. Единственное исключение — один LocalScript (`src/client/CustomCartUI.client.lua`), нужный ради кастомного вида промпта "взять тележку" и статичной экранной подсказки "отпустить тележку". Вся игровая логика по-прежнему на сервере — клиент ничего не решает, только просит через RemoteEvent, сервер сам проверяет владение.

## Главный цикл

Шахта автоматически (раз в 2 сек, скорость фиксирована) кладёт кристалл в тележку, стоящую в её зоне → тележка визуально наполняется слоями → игрок везёт её в центральный банк → в золотой зоне кристаллы по одному улетают в банк, деньги получает **текущий держатель** тележки.

По дороге любой игрок без тележки может ударить киркой — и по телу жертвы, и по самой тележке (она физически волочится позади владельца и тоже валидная цель): урон прилетает **одновременно и игроку, и тележке** (у неё своё ХП, зеркалящее ХП держателя), жертва получает микро-стан, часть кристаллов из тележки **и** часть руды из рук физически разлетаются по дороге. Добьёте тележку до нуля ХП — она "ломается": весь груз высыпается сразу, тележка открепляется и становится ничьей.

Своя тележка недоступна чужим игрокам, пока стоит на месте или в руках владельца — украсть можно **только** ту, что осталась на земле после смерти держателя. С тележкой в руках можно прыгать, но не часто — после каждого прыжка на 3 сек откат.

## Intro-катсцена Moon Animator 2

Порядок запуска для нового игрока: **загрузка ассетов → локальная катсцена → игра и интерактивный туториал**.

### Гайд для новичка

Ниже порядок действий буквально по кликам. Объекты сцены могут находиться в любом месте внутри `Workspace`. Загрузчик preload-ит весь `Workspace`, затем запускает катсцену.

#### Шаг 1. Установи Moon Animator Players

1. Открой Roblox Studio и свою игру.
2. Открой `Toolbox` → вкладка `Creator Store`.
3. Найди **Moon Animator 2 Players** и вставь его в игру.
4. В окне `Explorer` проверь, что появилась такая структура:

   ```text
   ReplicatedStorage
   └─ MoonAnimator2Players (Folder)
      ├─ MoonAnimatorPlayer_V2 (ModuleScript)
      ├─ Moon2Players_Retargeting (ModuleScript)
      └─ третий ModuleScript из asset
   ```

   Главный модуль для проигрывания сцены — `MoonAnimatorPlayer_V2`. Папку `MoonAnimator2Players` и остальные файлы переименовывать не нужно. `Moon2Players_Retargeting` нужен только для замены персонажей и в обычной катсцене не подключается вручную.

    Если ты используешь `rojo serve`, проект уже настроен сохранять вручную добавленные объекты внутри `ReplicatedStorage` и `Workspace`. Moon Animator, `StringValue` и содержимое сцены не должны исчезнуть при синхронизации.

#### Шаг 2. Создай временный мир катсцены

1. В `Explorer` открой `Workspace`.
2. Размести в `Workspace` все объекты второй карты: землю, NPC, декорации и всё, что будет двигаться в Moon Animator.
3. Объекты можно оставить прямо в `Workspace` или организовать в папки и модели.
4. Все детали должны иметь те же имена и вложенность, которые будут использоваться в анимации.

Пока ты создаёшь анимацию, все объекты должны находиться в `Workspace`, потому что Moon Animator сохраняет их полные пути. Записывай объекты именно из того места, где они будут находиться во время игры.

#### Шаг 3. Создай анимацию

1. Открой Moon Animator 2.
2. Создай новую animation sequence.
3. Добавь в неё объекты из любого места внутри `Workspace`.
4. Добавь камеру и персонажей, если они нужны.
5. Проиграй сцену в Studio и проверь, что всё двигается.
6. Сохрани сцену под именем `IntroCutscene`.

После сохранения Moon Animator создаст:

```text
ServerStorage
└─ MoonAnimator2Saves
   └─ IntroCutscene (StringValue)
```

#### Шаг 4. Оставь второй мир в Workspace

После сохранения анимации все объекты должны остаться в `Workspace`:

1. В `Explorer` проверь, что объекты находятся в `Workspace`.
2. Не перетаскивай сцену в `ServerStorage` или `ReplicatedStorage`.
3. Итог должен выглядеть так:

   ```text
   Workspace
    ├─ земля второй карты
    ├─ NPC и декорации
    ├─ точки камеры
    └─ остальные объекты сцены
   ```

Папки не имеют свойства `ModelStreamingMode`. Если используется `StreamingEnabled`, каждая `Model`, содержащая объекты сцены, должна иметь `ModelStreamingMode = Persistent` или `Atomic`.

#### Шаг 5. Установи репликацию Moon Animator

Камера Roblox локальная, поэтому сервер отправляет `StringValue` клиенту через SDK. Сам `StringValue` остаётся в `ServerStorage`.

1. В исходном проекте SDK уже подключён: `Moon2PlayersBootstrap.server.lua` запускает серверную часть автоматически.
2. `Moon2PlayersBootstrap.client.lua` загружает клиентскую часть автоматически и сообщает серверу о готовности.
3. Поэтому вручную переносить папки SDK между сервисами не нужно.
4. Проверь итог:

   ```text
     ReplicatedStorage
     ├─ MoonAnimator2Players
     │  └─ MoonAnimatorPlayer_V2
     └─ Moon2Players_Client
        └─ API (ModuleScript)
     └─ Moon2Players_Server
        └─ API (ModuleScript)

    ServerScriptService
    └─ Server
       ├─ Moon2PlayersBootstrap (Script)
       └─ Main (Script)

   ServerStorage
   └─ MoonAnimator2Saves
      └─ IntroCutscene (StringValue)
   ```

Копировать `IntroCutscene` в `ReplicatedStorage` не нужно. Серверный bootstrap автоматически берёт сохранения из `ServerStorage/MoonAnimator2Saves`, а клиент получает их через `Moon2Players_Client.API:WaitForAnimation`.

#### Шаг 6. Настрой StreamingEnabled

Если в игре включён `StreamingEnabled`:

1. Выбери каждую модель, участвующую в катсцене.
2. Найди `ModelStreamingMode`.
3. Поставь `Persistent` или `Atomic`.

Не оставляй анимируемые модели в потоковом состоянии `Default`: к моменту `MoonAnimatorPlayer.new()` все объекты и их дочерние части должны быть доступны клиенту.

#### Шаг 7. Проверь настройки

Открой файл `src/shared/Config.lua` и проверь:

```lua
Config.Cutscene = {
    Enabled = true,
    AnimationName = "IntroCutscene",
    FrameRate = 60,
    Duration = 10,
}
```

Все объекты сцены должны постоянно находиться в `Workspace`. В сохранённой анимации пути должны начинаться так:

```text
Workspace/HumanoidCameraRig
Workspace/NPC
Workspace/Ground
```

Не меняй имена и вложенность объектов после экспорта. Если путь в сохранении отличается от пути в игре, объект не будет найден.

`Duration` укажи равным длине сцены в секундах. Например, сцена на 18 секунд должна иметь `Duration = 18`.

#### Шаг 8. Запусти игру

Нажми `Play`:

1. Появляется loading screen.
2. Загружаются обычные ассеты игры.
3. Клиент загружает ассеты всего `Workspace`.
5. Запускается катсцена.
6. После `Ended` Moon Animator уничтожается, а объекты сцены остаются в Workspace.
7. Возвращается камера игрока.
8. Появляются игра и интерактивный туториал.

Если что-то не работает, открой `View` → `Output`. Частые ошибки:

- `MoonAnimatorPlayer_V2 was not found` — папка `MoonAnimator2Players` лежит не прямо в `ReplicatedStorage` или внутри неё нет главного ModuleScript `MoonAnimatorPlayer_V2`.
- `Animation was not replicated` — не установлен `Moon2Players_Server`, `Moon2Players_Client` или не найден `ServerStorage/MoonAnimator2Saves/IntroCutscene`.
- `Missing animation path` — объект отсутствует в `Workspace`, находится по другому пути или ещё не загружен Streaming.
- Сцена двигает не те объекты — после записи изменились имена или вложенность.
- `Workspace:WaitForChild(...)` — проверь, что все объекты сцены находятся в `Workspace` до создания проигрывателя.

### Настройки запуска

В `src/shared/Config.lua` укажи имя `StringValue`, FPS и фактическую длительность сцены:

```lua
Config.Cutscene = {
    Enabled = true,
    AnimationName = "IntroCutscene",
    FrameRate = 60,
    Duration = 10,
}
```

`LoadingScreen.client.lua` сначала ждёт завершения `ContentProvider:PreloadAsync` для всех доступных объектов игры, включая весь `Workspace`. После этого через `Moon2Players_Client` получает `IntroCutscene`, загружает `MoonAnimatorPlayer_V2` и вызывает `new(data, FrameRate)`. Проигрывание ждёт официальный сигнал `Player.Ended`; по окончании вызываются `Stop()` и `Destroy()`, камера возвращается игроку, а объекты сцены остаются в Workspace. `CustomCartUI.client.lua` не создаёт интерактивный туториал, пока катсцена не закончена.

### Важные ограничения Moon Animator

- Используй `animator:Start()` и `animator:Stop()`, с двоеточием.
- Не анимируй несуществующее свойство `Model.CFrame`; для модели используй поддерживаемый Moon Animator способ перемещения.
- Все части сцены должны существовать до создания проигрывателя.
- Если используешь события, подключай `animator:GetEventSignal()` до `Start()` и обрабатывай Lua-событие самостоятельно: код, сохранённый внутри события Moon Animator, модулем не выполняется.
- Для retargeting сохраняй reference-объекты, включая `ObjectValue`, если они есть в сохранённой анимации.

### Проверка в Studio

Запусти `Play` и дождись заполнения loading bar. После исчезновения loading screen должна начаться сцена, затем должен появиться обычный HUD и туториал. Если сцена пропущена, смотри Output: загрузчик явно сообщит, отсутствует ли реплицированная анимация `IntroCutscene`, `MoonAnimator2Players` или произошла ошибка API. Игра при этом продолжит запускаться, чтобы неправильная настройка сцены не заблокировала игроков.

### Кристалл-Model: как теперь можно класть внутрь что угодно

Раньше кристалл был обязан быть одним голым `Part`. Теперь — необязательно: можно положить `Model` с любым содержимым (доп. геометрия, `ParticleEmitter`, `PointLight`, что угодно), при одном условии — внутри обязателен `PrimaryPart`, названный **`Root`**. Это та часть, с которой физически работает вся остальная игра (падение/полёт/коллизия/крепление в слот тележки) — единая точка правды лежит в `CrystalUtil.GetRoot(crystal)`, ей пользуются `CrystalService`, `CartService` и `BankService`. Всё остальное внутри модели просто **приваривай к `Root` через `WeldConstraint`** (тот же принцип, каким у тележки-плейсхолдера стенки/колёса приварены к её `Root`) — тогда оно будет ездить/падать/лететь вместе с ним само, без единой строчки отдельного кода.

Каждый кристалл, ложась в слот тележки, получает случайный поворот на 0/90/180/270° вокруг вертикальной оси (`CartService:slotOffset`) — чисто визуальное разнообразие, одинаковые кристаллы не лежат все строго одинаково. Поворот запекается прямо в целевой `CFrame` слота, поэтому фиксируется в сварке (`weld.C0`) навсегда — не крутится каждый раз заново и не сбрасывается.

Размер плейсхолдер-кристалла (`PlaceholderFactory.crystalSize`) считается ОТНОСИТЕЛЬНО шага сетки (`Config.CartSlots.Cell`, 1.8 студ), а не фиксированным числом — раньше кристалл тира 8 (1.872 студ) был физически КРУПНЕЕ самой ячейки, гарантированно наезжал на соседей в сетке (мерцание/наложение текстур). Диапазон 0.85–1.45 студ (тир 1 → тир 8) с запасом меньше клетки, плюс случайный разброс ±8% на каждый экземпляр ("один чуть меньше, другой чуть больше") — даже в худшем случае (максимальный тир + максимальный разброс) сосед не задет.

Разброс ±8% применяется и к своему `Crystal_TierN`-ассету тоже — но только он, БАЗОВЫЙ размер твоей модели код не трогает и не подгоняет под сетку (ты сам выбрал его под свой масштаб). Для `Model` разброс накатывается через `Model:ScaleTo()` (масштабирует всю сборку целиком относительно размера "как было при вставке", не накапливается от повторного использования), для одиночного `Part` — просто множится `Size`.

### Щит — своя модель VFX + зелёная обводка, никакого ForceField

Пока игрок под защитой — над его головой на высоте `Config.Protection.VfxHeight` виден VFX-эффект (обычный ассет `ShieldVfx` в `ReplicatedStorage/Assets`, `BasePart` или `Model` с `PrimaryPart`/`Root` — нет своего ассета, используется плейсхолдер с зелёными искрами; см. `CombatService` — приварен к `Head`, не к тележке), а тележку (если она сейчас в руках) и персонажа обводит зелёный контур (`Highlight`, `CartService`/`CombatService`) — другим игрокам сразу видно, что грабить бессмысленно, не только по щиту у самого игрока в UI. `CombatService` включает/выключает все `ParticleEmitter` внутри `ShieldVfx` рекурсивно — не важно, лежат они прямо на части или на вложенном `Attachment`.

### Раскладка участка — тоже настраиваемая, не зашита в код

Раньше позиции шахты/пьедестала/спавна тележки/спавна игрока/НПС ребёрта были жёстко посчитанными смещениями прямо в `PlotService.lua`. Теперь это ассет `PlotTemplate` (см. таблицу выше) — обычная `Model` с полом (`PlotPad`) и пятью маркерами-`BasePart`, у каждого учитывается и позиция, И поворот. Собери свою раскладку в Studio как хочешь, положи в `ReplicatedStorage/Assets/PlotTemplate` — `PlotService` при старте сервера склонирует её по разу на каждый участок и просто прочитает `CFrame` каждого маркера вместо того, чтобы вычислять их сам.

**Где на карте стоит сам участок целиком — тоже можно расставить руками**, не только его внутреннее содержимое. По умолчанию кольцо участков вокруг банка по-прежнему считается кодом (`Config.World.PlotRadius`/`PlotCount`) — просто геометрия "N одинаковых слотов по кругу". Но если положить в `workspace` (не в `ReplicatedStorage/Assets` — это позиции конкретных мест на конкретной карте, не переиспользуемый шаблон) `Folder` с именем `PlotOrigins`, а внутрь — обычные `Part` (сколько нужно участков — столько частей) — `PlotService` использует их позицию И поворот как есть: где стоит и куда повёрнута часть — там и так стоит участок, лицом в ту же сторону. `Config.World.PlotCount`/`PlotRadius` в этом случае просто не используются.

**Поворот — как обычным вращением (Rotate), так и без него вообще**, если инструмент капризничает: положи рядом с частью-участком ещё одну с тем же именем и суффиксом `Look` (например, часть `Plot1` + `Plot1Look`) — направление СТРОГО ОТ первой КО ВТОРОЙ станет поворотом, двигать нужно только мышкой (Move), вращать не придётся. Тот же самый приём работает и для маркеров внутри `PlotTemplate` (см. ниже) — единый принцип везде.

Маркеры (и внутри `PlotTemplate`, и в `workspace/PlotOrigins`, и все `*Look`-компаньоны) после чтения позиции автоматически прячутся (`Transparency = 1`, `CanCollide = false`) — можно оставлять их в Studio любыми, не заботясь о том, что игрок увидит невидимый кубик.

**Декорации на участке — просто добавляй их в `PlotTemplate`, отдельно ничего строить не нужно.** Модель `PlotTemplate` клонируется на каждый участок целиком, со всем содержимым — если положить внутрь неё (рядом с обязательными маркерами) деревья, заборы, лампы, вообще что угодно ещё — они поедут на каждый участок автоматически, без единой строчки кода. Никаких специальных имён для декораций не нужно — не-маркеры код просто не трогает.

## UI (StarterGui, не код)

**v20: весь интерфейс в одном стиле, один билдер на всё — см. [`UI_V20_GUIDE.md`](UI_V20_GUIDE.md).**

Все экраны (HUD, хотбар, магазины, квесты, окна жеод/скинов/перков/островов, мини-игры, обучение,
подсказки промптов, лента добычи, баффы…) собирает `tools/BuildAllUI.lua` в `StarterGui` — дальше их
можно менять в Studio, игра использует именно их. Мировые надписи (над рудой, NPC, мобами) берут стиль из
`StarterGui/WorldUiTemplates`. Если экрана в StarterGui нет или он собран старым билдером, клиент соберёт
его сам тем же билдером (`Shared/UiRegistry`), так что игра без UI не останется.

`ScreenGui.ResetOnSpawn` у всех экранов `false` — респавн в игре ручной (`CharacterAutoLoads = false`).

**Весь игровой текст — на английском**, русский перевод подставляет `Shared/Localization` по языку игрока.

### Меню настроек — звук и промокоды

Шестерёнка в **левом верхнем** углу, открывает панель. **Звук** — чисто клиентская настройка: все звуки (`Sfx.lua`) идут через один `SoundGroup "SFX"` в `SoundService`, который создаёт сервер при старте; переключатель в меню просто крутит `SoundGroup.Volume` у себя локально — сервер и другие игроки ничего не замечают, никакого `RemoteEvent` для этого не нужно.

**Промокоды** — сервер сам проверяет валидность и повторное использование (`DataService:RedeemCode`, `RemoteEvent "RedeemCodeRequest"`), клиенту нечего подделывать. Список кодов и наград — `Config.PromoCodes` (сейчас `DISCORD` и `LAUNCH`, каждый разово на аккаунт — использованные хранятся в `profile.Data.RedeemedCodes`). Ввод кода — `Enter` в текстовом поле или кнопка `Claim`; во время печати клавиши `1`/`E` (экипировка кирки/удержание отпускания тележки) временно не перехватываются (`UserInputService:GetFocusedTextBox()`), чтобы не мешать вводу.

### Хотбар кирки и визуальный откат

Дефолтный Backpack Roblox выключен (`StarterGui:SetCoreGuiEnabled(Enum.CoreGuiType.Backpack, false)`) — вместо него слот F в центре хотбара (`StarterGui/HotbarUi/PickaxeSlot`), т.к. в игре всего один инструмент и полноценный инвентарь не нужен. **Важный нюанс** (задокументировано на форуме разработчиков Roblox): отключение Backpack CoreGui вырубает не только визуал, а вообще всю штатную систему экипировки инструментов — хоткеи 1-9 и клик по слоту тоже перестают работать. Поэтому: сервер сразу выдаёт кирку в руки при создании (`tool.Parent = character`, а не `Backpack` — `CombatService:_giveTool`), жать ничего не обязательно; клавиша `1` и клик по слоту (`CustomCartUI.client.lua`) реализованы вручную через `Humanoid:EquipTool()`/`UnequipTools()` — чисто опциональная возможность "убрать"/"вернуть" кирку.

Иконка берётся из `Config.Icons.Pickaxe` — просто число (ID картинки из каталога/Asset Manager, без `rbxassetid://`, префикс достраивается кодом сам). Пока `0` — на её месте emoji-плейсхолдер ⛏️. Тонируется цветом текущего тира кирки (`Config.PickaxeTiers[N].VfxColor`) через атрибуты игрока `PickaxeTier`/`HasPickaxe` (сервер выставляет их в `CombatService`, реплицируются сами, отдельный RemoteEvent не нужен).

Кулдаун визуализирован тёмной заливкой, которая "стекает" сверху вниз по мере отката (заполнена целиком сразу после удара → пусто, когда можно бить снова), плюс число секунд до готовности. Сервер после каждого ПРИНЯТОГО (не отклонённого кулдауном) взмаха шлёт `PickaxeSwungEvent` — клиент сам знает длительность отката из `Config.PickaxeTiers[тир].Cooldown` (тир уже известен через атрибут), поэтому в самом событии передавать нечего.

## Бой: хитбокс, микро-стан, ХП тележки

### Хитбокс — реальный прямоугольник, не круг+сектор

Попадание кирки больше не считается "дистанция + угол перед носом атакующего" — теперь это настоящий параллелепипед перед атакующим в его локальных координатах (`Config.Combat.HitboxSize` — ширина/высота/глубина, `HitboxForwardOffset` — насколько выдвинут вперёд). `findVictim` в `CombatService` проверяет попадание точки цели именно в этот параллелепипед через `CFrame:PointToObjectSpace`. Растёт вместе с тиром кирки (`Config.PickaxeTiers[тир].Scale`), как и модель самой кирки.

**Отладочная визуализация — это ТА ЖЕ геометрия**, не отдельная прикидка: `Config.Debug.ShowCombatHitbox = true` рисует полупрозрачный параллелепипед ровно такого же размера/положения, какой реально проверяется на попадание (`debugDrawHitbox` использует те же `Config.Combat.HitboxSize/HitboxForwardOffset`) — что видишь, то и бьёт. Выключается одним флагом в Config, когда калибровка закончена.

**Тележка держателя — тоже валидная цель**, наравне с его телом: она физически волочится позади игрока, и удар, нацеленный именно в неё, а не в тело владельца, засчитывается так же (тот же урон, микро-стан, выбитие руды) — `findVictim` проверяет попадание и в HRP игрока, и в тележку, что ближе — то и цель. Если в модели тележки есть отдельная часть `Hitbox` (см. таблицу плейсхолдеров выше) — берётся ближайшая точка на её поверхности (реальная область, по которой можно попасть, а не только центр); нет её — засчитывается только точка в центре `Root`, как раньше.

### ХП тележки зеркалит игрока

При захвате тележки (`CartService:Attach`) её `MaxHealth`/`Health` выставляются равными `Humanoid.MaxHealth` текущего держателя и сбрасываются на полное при каждом новом захвате (свежая в руках тележка всегда целая, не "подранная" с прошлой жизни или чужого владения). Каждый удар наносит **одинаковый** урон и игроку, и тележке (`CombatService:ApplyHit` → `CartService:DamageCart`). Дойдёт ХП тележки до нуля — она "ломается": весь оставшийся груз высыпается на дорогу той же гарантированной "выброс наружу" физикой, что и обычное выбитие (см. ниже), а сама тележка тут же открепляется и становится доступной для угона — как будто держатель погиб.

### Микро-стан + лёгкая тряска

Каждый удар (кирка, попадание по телу или по тележке) на `Config.Combat.MicroStunDuration` (1.5 сек) обнуляет скорость жертвы (`CombatService:IsStunned`, читается общей функцией расчёта скорости в `CartService`, поэтому не спорит с замедлением от груза тележки/рук) — не мгновенный разворот жертвы обратно в контратаку или за выбитой рудой, а реальное окно для атакующего. Сопровождается едва заметной тряской на месте (не перемещением!) — `AlignPosition` с крошечной случайной целью, обновляется каждые `Config.Combat.StunShakeInterval` (0.05 сек) с амплитудой `StunShakeAmplitude` (0.18 студ) — чисто визуальная обратная связь "тебя оглушили", гаснет сама вместе со станом. Тряска обёрнута в `pcall` — если она вдруг упадёт с ошибкой, сам стан (обнуление скорости и его снятие по таймеру) от этого не сломается.

### Выбитие руды — гарантированно "наружу", как в Fortnite

И кристаллы из тележки, и руда из рук (см. ниже) при выбитии улетают по направлению, посчитанному математически (случайный угол по кругу + фиксированная горизонтальная/вертикальная скорость, `Config.Combat.KnockoutEjectOutSpeed/UpSpeed`), а не изотропным рандомом — физически не может приземлиться обратно внутрь тележки. На время полёта (`KnockoutEjectNoCollideTime`, 0.6 сек) коллизия с источником (ВСЕМИ частями тележки — стенки/колёса, не только пол; или всем телом жертвы) временно отключена через `NoCollisionConstraint` — раньше кристалл мог физически застрять в геометрии едущей тележки, теперь нет.

### Подбор выбитой руды — блокировка только для владельца

Первые `Config.Crystal.PickupLockoutTime` (5 сек) выбитый кристалл может подобрать **кто угодно, кроме владельца** — микро-стан и так не даёт жертве среагировать мгновенно, а этот таймер не даёт ей же подобрать свою выбитую руду раньше вора, если та каким-то образом до неё дотянется. Дальше — по-разному:
- **Владелец** (у кого выбили/кто уронил при смерти) — летит в тележку, если есть место, иначе в руки.
- **Кто угодно ещё** — только в руки (см. `HandCarryService`), даже если рядом пустая тележка: грабёж чужой добычи ограничен вместимостью рук по тиру кирки, а не размером собственной тележки грабителя.

## Руда в руках (без тележки)

`HandCarryService` — способ подбирать выбитую в бою руду голыми руками, без необходимости красть/тащить целую тележку.

- **Вместимость** зависит только от тира кирки (`Config.HandCarry.CapacityByPickaxeTier`, индекс = тир 1..8): `2, 4, 6, 8, 10, 10, 10, 10` — растёт с прокачкой кирки, упирается в потолок на тире 5.
- **Замедление**: ~5.5% скорости за каждый кусок на горбу (`Config.HandCarry.SlowdownPerItem`), потолок 50% (`MaxSlowdown`). Считается той же единой функцией, что и нагрузка тележки (`CartService`, `recomputeWalkSpeed`) — если несёте одновременно и тележку, и что-то в руках, замедления перемножаются, а не спорят друг с другом через прямые перезаписи `WalkSpeed`.
- **Видно на спине** — растущий стек цветных кубиков (цвет = тир каждого подобранного кусочка), с подписью "✋ N/Cap" над стеком.
- **Не грабится в PvP хитом другого игрока** сама по себе — НО удар выбивает часть и из рук тоже (та же формула %/максимума, что и у тележки, см. `CombatService:ApplyHit`) — то есть безопасна только от "тихой" кражи, не от честного боя.
- **Роняется при смерти держателя**, как и содержимое тележки — тот же риск потери добычи.
- **Продаётся в той же золотой зоне банка**, что и тележка (привязано к позиции игрока, не тележки — своего `Root` у стеша рук нет), с той же анимацией "улетает и растворяется", но **без комбо-множителя тележки** — компромисс "безопасно, но менее выгодно".

## Владение и кража

- **Пьедесталы прокачки, кнопка респавна тележки, NPC ребёрта** — уже были и остаются владелец-only: каждый промпт проверяет `triggerer == player` (владелец участка) перед срабатыванием.
- **Добыча из чужой шахты физически невозможна**: цикл добычи (`MineService`) всегда сверяется только со своим участком (`PlotService:GetPlot(player)` — участок именно ДЕЙСТВУЮЩЕГО игрока), физически стоять у чужой шахты бесполезно.
- **Своя тележка недоступна другим игрокам**, пока просто стоит на месте или в руках владельца — `Attach()` отказывает всем, кроме владельца (`OwnerUserId`), пока не взведён флаг `Stealable`. Флаг взводится **только** когда держатель тележки погибает (`Humanoid.Died` → `Detach(data, true)`) — с этого момента её может забрать кто угодно, пока законный владелец не заберёт её обратно (тогда флаг гасится).

## Единственный LocalScript в проекте — зачем он

Кастомный вид `ProximityPrompt` (Style = Custom) технически требует клиентского рендера — так устроен сам Roblox: без LocalScript либо стандартный вид, либо ничего. `src/client/CustomCartUI.client.lua`:
- слушает **глобальный** `ProximityPromptService.PromptShown/Hidden/ButtonHoldBegan/ButtonHoldEnded` (не привязан к конкретному инстансу) и рисует свою рамку с бейджем клавиши `E` и полоской удержания — сработает для любого промпта с `Style = Custom` в игре, сейчас это только "Взять тележку";
- показывает статичную подсказку "Отпустить тележку" на экране, пока у игрока `Attribute("CarryingCart") == true` (атрибут уже реплицируется сервером сам, без доп. кода) — не мигает при ходьбе, потому что не завязана на мировую близость;
- по нажатию `E` во время переноски шлёт `RemoteEvent("DropCartRequest")` — **сервер сам проверяет**, что отправитель реально держит тележку, прежде чем её отпустить;
- строит и подключает меню настроек (шестерёнка/звук/промокоды), устойчивое к любому типу GUI-объектов (см. `connectClick` выше);
- строит и подключает диалог NPC-продавца прокачки — реплика типируется посимвольно прямо над головой NPC (BillboardGui `Head/gui`, стиль Fisch/Grow a Garden), варианты ответа — отдельным пронумерованным списком на экране (клик или клавиши 1/2/3), камера слегка приближается на время разговора; сам ничего не считает, только шлёт `RemoteEvent("UpgradeShopRequest")` и рисует статус, который прислал сервер.

Никакой другой логики на клиенте нет и не появится без явного запроса — весь остальной проект как был, так и остаётся server-authoritative.

## Принятые инженерные решения (в рамках ТЗ, всё в Config)

### Тащить тележку — анимация, а не физика рук

Раньше здесь была механика честного растягивания рук до ручек тележки (Motor6D на R6, IKControl на R15). Отказались от неё в пользу простого и надёжного решения: пока тележка в руках, у держателя подменяются штатные Idle/Walk на анимации "тащит тележку" (`Config.Animations.CartIdle/CartWalk`, `Enum.AnimationPriority.Action` — перебивают дефолтную анимацию персонажа). Оба ID сейчас `rbxassetid://0` (плейсхолдеры) — если не заданы, анимация просто не проигрывается, без ошибок; тележка при этом всё равно нормально едет и не ломает остальную механику. Прыгать с тележкой в руках можно, но с откатом (`Config.Cart.JumpCooldown`, 3 сек) — не полный запрет через `SetStateEnabled`, а подписка на `Humanoid.StateChanged`: как только держатель прыгнул, `Jumping`-состояние на 3 сек отключается и включается обратно само.

Пол тележки (`Config.CartSlots`) шире по X (`Cols`), чем по Z (`Rows`) — без поправок держатель оказывался лицом к ШИРОКОЙ стороне (как будто толкает, а не тащит). `Config.Cart.HolderSideRotation` (90°) разворачивает саму тележку вокруг её же центра прямо в `Motor6D` (`C1`, см. `CartService:Attach`) — позиция крепления не меняется, только ориентация, так что к игроку обращена узкая сторона. Сетку слотов кристаллов это не трогает вообще: она считается в локальных координатах `Root` (`slotOffset`) и просто крутится вместе с тележкой как единое целое.

**Высота крепления тележки (`C0`) — статичное значение из `Config.Cart.FollowOffset` по умолчанию, никакой физики/проверок в рантайме нет вообще** (были две более сложные версии — расчёт по нижней точке модели, потом активная поправка каждый кадр — обе убраны, лишняя сложность для простой проблемы). Настраивается вручную через необязательную часть `AttachPoint` в модели тележки: её ЛОКАЛЬНАЯ высота относительно `Root` используется напрямую как `C0.Y`, без единого вычисления — подвинул деталь мышкой в Studio выше, тележка держится выше; подвинул ниже — ниже. Изменение видно сразу при следующем тесте (F5), никакого редактирования кода/конфига не требуется. Нет такой части в модели — используется число из конфига как раньше.

**Разворот тележки (`C1`) — по умолчанию общий угол на все тиры** (`Config.Cart.HolderSideRotation`), но у разных `Cart_TierN` может быть разная внутренняя ориентация модели — один угол не всегда подходит всем сразу (пример из практики: несколько кастомных тележек, у одной из них угол оказался не тот, хотя у остальных всё было верно). Чтобы настроить ИМЕННО эту модель — положи в неё `Part` с именем `FacingPoint` в направлении, которое должно "смотреть" на игрока: код сам считает угол через `atan2` по направлению от `Root` к этой части и разворачивает тележку соответственно (`CartService:Attach`), никаких чисел подбирать не нужно. Нет такой части — используется общий угол из конфига.

### Физика поворотов — тяжёлая тележка мешает резко разворачиваться

Пока тележка в руках, `Humanoid.AutoRotate` выключается — разворотом персонажа теперь управляет сам `CartService` через `AlignOrientation`-констрейнт на HRP держателя (не прямая запись CFrame — так поворот не конфликтует с физикой Humanoid и не дёргается при репликации). Угол поворота "доезжает" до направления движения с ограниченной угловой скоростью: `Config.Cart.MaxTurnRate` (пустая тележка — почти как обычно) до `Config.Cart.MinTurnRate` (полная тележка — медленный, тяжёлый разворот), линейно от % заполнения. `AutoRotate` возвращается в `true` при отпускании тележки.

### Прокачка: 3 независимые ветки с кросс-зависимостью, покупаются у NPC-продавца

Раньше на участке стояли три отдельных пьедестала (по одному на ветку), теперь — **один NPC-продавец** (`UpgradeShopNPC`, стоит там же, где раньше стояли пьедесталы — маркер `PillarMarker` шаблона участка, см. раздел про `PlotTemplate` выше). Подходишь, жмёшь `E` — NPC говорит текстом над своей головой (посимвольная печать, стиль как в Fisch/Grow a Garden — см. `Head/gui` в таблице выше), камера слегка приближается (`FieldOfView` 70→65), а **справа на экране** одна за другой (тоже посимвольно) печатаются три пронумерованные строки: Шахта / Тележка / Кирка, у каждой — текущий тир и цена следующего. Выбрать можно кликом ИЛИ клавишами `1`/`2`/`3` — купил, список остаётся открытым, можно сразу брать следующий апгрейд. Закрыть можно тремя способами: отойти от NPC дальше `Config.UpgradeShop.DialogRange` (14 студ), нажать `Escape`, либо кликнуть по крестику — во всех случаях камера возвращается.

**Технически:** вся логика покупки (проверка денег/тир-капа/гэпа между ветками) как и раньше живёт **только на сервере** (`UpgradeService:_tryBuy`) — диалог лишь отправляет `RemoteEvent "UpgradeShopRequest"` с просьбой купить конкретную ветку, а сервер сам решает, разрешить ли, и присылает обратно актуальный статус всех трёх веток. Клиенту в этой схеме нечего подделывать — он не считает ничего сам, только рисует то, что прислал сервер.

У каждого своего прогресс и своя стоимость (`Config.MineChain`/`CartChain`/`PickaxeChain`, по 7 шагов, тиры 2..8). **Зависимость между ветками:** нельзя купить тир, если он окажется больше чем на `Config.BranchMaxGap` (2) тира выше самой отстающей из двух ОСТАЛЬНЫХ веток — иначе пункт в диалоге пишет «Catch up other branches» и блокирует покупку.

### Ребёрт — НПС на КАЖДОЙ базе

У каждого игрока на его собственном участке стоит "Мастер Ребёрта" (`RebirthService:SetupPlot`, вызывается из `PlotService:AssignPlot` — та же схема, что и у пьедесталов прокачки).

**Тир-кап от ребёртов:** без единого ребёрта потолок тира — `Config.Rebirth.BaseTierCap` (5), а не физический максимум 8 — прокачать выше него нельзя ни в одной из 3 веток, пьедестал пишет "Нужен РЕБЁРТ (потолок тир N)". Каждый ребёрт поднимает потолок на `TierCapPerRebirth` (1), пока не упрётся в `MaxTierCap` (8, реальный предел цепочек) — то есть до тира 8 нужно 3 ребёрта при базе 5. НПС доступен, когда все 3 ветки прокачаны до ТЕКУЩЕГО потолка (`DataService:GetTierCap`), И на руках хватает денег на сам ребёрт (`Config.Rebirth.CostBase`/`CostGrowth`, растёт геометрически с каждым следующим). Ребёрт сбрасывает все три ветки и деньги (`Config.Rebirth.ResetMoney`) за постоянный множитель цены кристаллов (+50% за ребёрт) — множитель **запекается в кристалл при добыче**, вор получает полную «ветеранскую» цену. Заблокирован, пока тележка угнана.

### Замедление от груза — тележка + руки складываются, а не спорят

Единая функция расчёта скорости (`recomputeWalkSpeed` в `CartService`, вызывается и оттуда, и из `HandCarryService`, и из `CombatService` после стана) — считает по цепочке: база → нагрузка тележки (если несёт, зависит от % заполнения И разницы тиров Тележка/Шахта, как раньше) → груз в руках (если есть, см. `Config.HandCarry.SlowdownPerItem`) → микро-стан (если активен, перебивает всё нулём). Максимальная просадка от тележки не константа: база `Config.Cart.BaseMaxSlowdown` (65%) при РАВНЫХ тирах Тележки и Шахты; за каждый тир, на который **Тележка круче Шахты** — минус 15 п.п. (`SlowdownPerTierAdvantage`); за каждый тир, на который **Шахта круче Тележки** — плюс 15 п.п. Диапазон разницы тиров и так ограничен `Config.BranchMaxGap` (±2), пол/потолок — `MinSlowdown`/`MaxSlowdown` (30%–70%).

### Безопасность физики тележки

Сила и отзывчивость поворотного `AlignOrientation` заметно снижены (`Config.Cart.TurnMaxTorque/TurnResponsiveness`), упругость всех частей обнулена, плотность снижена (`CustomPhysicalProperties`, Elasticity=0, Density=0.4) — столкновение со стеной гасится, а не отскакивает рывком. Пока держит — коллизия отключена ТОЧЕЧНО между этой тележкой и именно этим игроком (`NoCollisionConstraint` между `Root` тележки и HRP игрока), со всем остальным миром и другими игроками тележка продолжает сталкиваться как обычно.

### Хват за тележку руками (R6 IK)

Пока держит тележку, руки персонажа визуально "прилипают" к точкам хвата на её модели — с "резиновым" растяжением: `Size` руки по Y каждый кадр подгоняется РОВНО под расстояние до цели, без верхнего предела, кончик руки всегда математически точно совпадает с точкой хвата (у R6-руки нет локтя — только разворот всей руки целиком, без сглаживания).

**Развязка с анимацией — переписана с нуля (v14).** Ключевое понимание: анимация ходьбы/стояния — это не свойство детали руки, а `Motor6D.Transform`, который `Animator` записывает в плечевые суставы КАЖДЫЙ кадр, находя их по имени внутри дерева персонажа в рантайме (итоговая поза детали = `Part0.CFrame * C0 * Transform * C1⁻¹`). Все прошлые подходы (переименование, клон руки, клон всего персонажа со скрытием оригинала, свой параллельный `Motor6D` с правкой `C0` в `RenderStepped`) боролись с аниматором не на том уровне и "протекали": канал `Transform` оставался открытым, а правки в `RenderStepped` вдобавок опаздывали на кадр относительно анимации торса (RenderStepped выполняется в начале конвейера кадра, анимация применяется после). Теперь с ригом не делается ВООБЩЕ ничего — ни клонов, ни скрытий, ни переименований, ни новых суставов: каждый кадр в `RunService.Stepped` (срабатывает СРАЗУ ПОСЛЕ записи Transform аниматором) `Transform` штатных `Left/Right Shoulder` просто перезаписывается своим прицеливанием. Аниматор пишет свою позу — мы каждый кадр детерминированно пишем поверх; утечка анимации невозможна по построению. Компенсация растяжения (плечевой конец остаётся в плече) зашита прямо в `Transform` — `C0`/`C1` не трогаются, при отпускании восстанавливается только `Size`, а `Transform` аниматор сам перепишет следующим кадром. Одежда/аксессуары/цвета — родные (рука — родная), ноги/торс анимируются как обычно.

**Видно всем игрокам.** `Motor6D.Transform` НЕ реплицируется, поэтому тот же код выполняется на КАЖДОМ клиенте для КАЖДОГО держателя (не только для себя): клиент находит все тележки с атрибутом `HolderUserId` (реплицируется сервером из `CartService:Attach`; мгновенно — по `GetAttributeChangedSignal`, страховочно — реконсиляцией раз в секунду против стриминга/поздней репликации) и ведёт IK их держателей локально — анимации чужих персонажей тоже проигрываются локально на каждом клиенте, так что перезапись в `Stepped` работает для них точно так же.

**Точки хвата.** Три уровня, по убыванию приоритета:
1. Маркеры `LeftHandGrip`/`RightHandGrip` в модели — если билдер расставил их вручную, используются как есть (сторону всё равно перепроверяет `assignGripSides` — см. ниже, имена маркеров сами по себе не гарантия).
2. **По умолчанию, без всякой разметки** — луч от РЕАЛЬНОГО положения плеча каждой руки в сторону центра тележки (`raycastGripOffset`), и берётся точка, где луч реально задевает геометрию модели — работает для любой формы (не только прямоугольного бампер-бокса), не гадает по габаритам. Сторона тут верна по построению: луч левой руки стартует из физически левого плеча персонажа, так что где бы он ни воткнулся в тележку — это по определению левая точка хвата, отдельной коррекции не требуется. `RaycastParams.FilterDescendantsInstances` ограничен самой моделью тележки — луч не может зацепить тело игрока, других игроков или рельеф; маркеры-ориентиры (`AttachPoint`/`FacingPoint`/`Bottom`/`LeftHandGrip`/`RightHandGrip`) сервер и так делает `CanQuery = false` при постройке — лучу они не видны.
3. Совсем крайний случай (луч ничего не задел — например, у тележки временно нет ни одной `CanQuery`-части) — старый рандомный, но ДЕТЕРМИНИРОВАННЫЙ фолбэк по габаритам `Root` (`Random` сидируется атрибутом `GripSeed`, сервер ставит его при захвате и снимает при отпускании — все клиенты независимо приходят к одной и той же точке), с той же коррекцией стороны, что и у маркеров.

**Коррекция стороны (`assignGripSides`).** Названия маркеров и геометрический "фолбэк №2" сами по себе не гарантия физической стороны — тележка крепится через `FollowOffset`+`HolderSideRotation` (см. `Config.Cart`), которые в сумме ощутимо заворачивают её (по умолчанию тележка висит СЗАДИ игрока, ещё и довёрнута на 90°). Поэтому для этих двух способов сторона определяется по факту, один раз при захвате: сравнивается, какая из двух точек реально лежит дальше вдоль настоящего `RightVector` торса — та и правая. Для раycast-способа (основного) эта коррекция не нужна вообще — луч физически стартует из нужного плеча, сторона верна изначально.

**Ширина плеч.** Точка крепления руки вынесена чуть дальше от центра торса (`ARM_SHOULDER_WIDEN_STUDS`) — рука растёт ИЗ плеча, а не из середины тела/утопает в торсе.

**Реальный физический люфт.** Тележка больше не приварена к игроку абсолютно жёстко (`CartService:Attach`) — вместо прямого `Motor6D` она физически ДОГОНЯЕТ невидимый "идеальный" якорь, который сам жёстко висит на игроке ровно так же, как раньше висела сама тележка. Догоняет через `AlignPosition`/`AlignOrientation` с конечной силой и ОТЗЫВЧИВОСТЬЮ (`Config.Cart.FollowResponsiveness` — специально невысокая, самокоррекция растягивается на секунду-другую, а не мгновенная). При резком движении/повороте игрока тележка на мгновение реально физически чуть отстаёт — и вот от этой самой честной дистанции руки визуально чуть растягиваются, а через секунду-другую тележка и вместе с ней хват снова точно на месте. HP/урон по-прежнему считаются от `Root` тележки.

**Коллизия с игроками — отдельная физическая "вселенная" (PhysicsService).** Тележка и персонажи игроков лежат в разных коллизионных группах (`CART_COLLISION_GROUP`/`PLAYER_COLLISION_GROUP` в `CartService.lua`), между которыми столкновения выключены раз и навсегда через `PhysicsService:CollisionGroupSetCollidable` — тележка никогда не толкает и не расталкивает ни держателя, ни случайных игроков, ни в руках, ни стоя на земле. С миром (землёй/стенами — они всегда в группе `Default`) обе группы продолжают сталкиваться как обычно. Раньше эта развязка делалась грубее — полным отключением `CanCollide` у всех частей тележки на время удержания, — из-за чего тележка переставала сталкиваться и с игроками, И С ЗЕМЛЁЙ одновременно: на резком скачке `HRP` вверх (прыжок) она на мгновение проседала ниже упругой привязки и, не встречая пола, проваливалась под карту. Коллизионные группы решают это не трогая мировую коллизию вообще — падать сквозь рельеф тележке больше физически нечем.

### Пыль под тележкой на ходу (SprintVFX)

Под задней частью КАЖДОЙ тележки (любой тир, плейсхолдер или свой ассет `SprintVFX` из таблицы выше) код сам ставит деталь и варит её на место. Партиклэмиттер уже лежит ВНУТРИ самого ассета `SprintVFX` — код его не создаёт и не настраивает, только позиционирует саму деталь (пока своего ассета нет — используется плейсхолдер со своим простым эмиттером, чтобы не было пусто).

"Задняя" сторона (куда крепится эффект) определяется так же, как и остальная геометрия тележки: явный маркер `SprintVFXPoint` в своей модели — высший приоритет; иначе — зеркально от `FacingPoint`, если он есть; без обоих маркеров — тот же дефолт, что и у `HolderSideRotation` (сторона, противоположная той, что обращена к игроку), вычисляется от размера `Root` — работает для любой модели без дополнительной настройки.

### Экономика

Руда — 8 тиров, цена растёт линейно: множитель = номер тира (`x1..x8`, `CrystalValue = 8 × Multiplier`), виден прямо над каждым кристаллом рядом с ценой (`x3 · $24`). У каждого тира есть ещё и отдельная шкала `Points` (1/3/8/15/26/42/65/95) — она не про деньги, а про комбо-множитель тележки (см. ниже), специально нелинейная и её можно менять независимо от цены.

### Комбо-множитель тележки

Зависит от % заполнения тележки НАПРЯМУЮ, а не от абсолютных очков — комбо начинается, только когда тележка ощутимо заполнена. Формула (`comboMultiplier` в `CartService`): `effectiveFill = (заполнение, 0..1) × (среднийPoints / Config.Cart.ComboReferencePoints)` — ценная руда работает как ускоритель: тот же множитель даётся при МЕНЬШЕМ % заполнения, то есть прокачка Шахты (более высокий тир добываемой руды → выше средний `Points`) напрямую поднимает потолок комбо при той же загрузке тележки. Ниже `Config.Cart.ComboMinFill` (15%) комбо не считается вообще. 16 порогов в `Config.Cart.ComboThresholds`, от x1.5 до x120. Тележка физически не может быть заполнена больше 100% (`AddCrystal` отказывает, когда слоты кончились), поэтому потолок каждого тира руды достигается ровно на полной тележке: при 100% заполнения тиры 1-6 упираются в x50, а тиры 7 и 8 — в x80 и x120 соответственно (у них выше "буст" от Points, поэтому и потолок выше). При 60% физического заполнения: тир 1 даёт x2, тир 8 — около x35. Множитель **фиксируется в момент захода в золотую зону**, чтобы не таял на глазах по мере продажи. Руда в руках комбо-множитель не получает никогда — это осознанный компромисс "безопасно, но менее выгодно".

Визуальная карточка комбо растёт вместе с множителем по 6 "лигам" (`Config.Cart.ComboVisualStages`): дерево (x1.5+) → серебро (x3+) → бронза (x8+) → золото (x18+) → кристалл (x35+) → радуга (x65+, физически достижима только у тиров руды 7-8 на почти полной тележке).

### Catch-Up и PvP

Урон и скорость атаки кирки — главная ось её прогрессии: тир 1 бьёт раз в 6.5 сек на 8 урона (почти не боец), тир 8 — раз в 1 сек на 46 урона. Тир кирки также увеличивает **выбивание кристаллов**: 15% (макс 4) на тире 1 → 50% (макс 18) на тире 8 — та же формула применяется и к выбитию руды из рук, и (тем же числом урона) к ХП тележки. VFX удара — серверные `ParticleEmitter`, клиентских скриптов не требуют.

**Защита** (`Config.Protection`) — кнопка на экране (щит 🛡️, рядом с кнопкой "Заспавить тележку"): 30 сек бесплатной неуязвимости, кулдаун 3 минуты до следующей. Защищённого нельзя выбрать целью вообще (`findVictim` его пропускает) — но если он САМ атакует кого-то, защита тут же спадает — честная "передышка", а не бесплатная неуязвимость для агрессии. Пока кнопка на кулдауне, клик пытается купить платное продление (+60 сек) через настоящий Developer Product Roblox — **`Config.Protection.PaidProductId` нужно создать вручную в Studio/Creator Dashboard и вписать ID** (пока `0` — кнопка предупреждает в логах и ничего не делает).

Пока держатель защищён — над самой тележкой виден VFX-эффект щита и зелёная обводка тележки/персонажа (см. раздел про щит выше) — другим игрокам сразу видно, что грабить бессмысленно, не только по щиту у самого игрока в UI.

### Деспавн и ручной респавн тележки

Свободную (никто не держит) тележку, которую не трогали дольше `Config.Cart.DespawnIdleTime` (45 сек) — уничтожает полностью, груз внутри теряется. Если это была ТЕКУЩАЯ тележка игрока — тут же спавнится пустая новая на его базе.

Кнопка "Заспавить тележку" — **физическая, стоит в мире у парковки** (не UI!), рядом с `CartParkingPad`. Всегда доступна (кулдаун `Config.Cart.ManualRespawnCooldown`, 3 минуты) — пока на кулдауне, крышка кнопки визуально "вдавлена", выскакивает обратно и снова светится, когда снова можно нажимать. Отсчёт секунд над кнопкой — только в последние `Config.Cart.RespawnCountdownThreshold` (30) секунд.

### Билборды — постоянный размер на экране

Все `BillboardGui` в проекте используют `Size` через **Scale**, а не через `Offset` — так размер на экране не зависит от расстояния до камеры.

### Прочее

- Кристалл хранит свою цену в атрибуте: угнанная тележка/выбитая руда с дорогими кристаллами приносит вору полную стоимость.
- Данные = `Money` + прогресс 3 веток (`MineIndex/CartIndex/PickaxeIndex`) + `RedeemedCodes` (использованные промокоды) — тир каждой ветки хранится напрямую.
- Звуки: у добычи, PvP, тележки, продажи и апгрейдов — свои (`Config.Sounds`). Все ID — плейсхолдеры `rbxassetid://0`, замени на свои. Все идут через один `SoundGroup "SFX"` — клиент может приглушить их локально через меню настроек, не трогая сервер.
- Тележка спавнится на ОТДЕЛЬНОЙ парковке участка (`plot.CartSpawnCFrame`, свой пятачок `CartParkingPad` позади шахты/пьедестала) — не привязана к позиции шахты и не съезжает при её апгрейде.

## Архитектура

Один Script (`Main`) + независимые ModuleScript-сервисы с `Init(Services)/Start()`: Data, World, Crystal, HandCarry, Cart, Plot, Mine, Bank, Upgrade, Combat, Hud, Rebirth. Плюс один LocalScript (`CustomCartUI`) — единственное клиентское исключение, чисто UI, без игровой логики. Все балансные числа — в `Config.lua`. Все модели — только через `PlaceholderFactory` (плюс `CrystalUtil` — общая точка правды "где у кристалла физическая часть", нужна из-за поддержки Model-кристаллов). Общие мелкие утилиты — `Sfx.lua`, `NumberFormat.lua`.
